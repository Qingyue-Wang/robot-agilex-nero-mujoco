# Nero MoveIt config (self-contained, for the MuJoCo sim)

MoveIt2 planning config for the simulated AgileX Nero arm, wired to the MuJoCo
sim in this repo. It is a **self-contained** copy of the AgileX
`nero_gripper_moveit_config` package with the broken `agx_arm_description` URDF
import replaced by the sim's own kinematic tree, so `move_group` plans against
the exact same geometry the bridge simulates.

## Layout

```
moveit/
  nero_gripper_moveit_config/   the MoveIt config package (config/ + launch/)
  cartesian_demo.py             headless Cartesian demo (raw rclpy, no moveit_py)
  build.sh                      builds the config into moveit/ws (colcon overlay)
  ws/                           build artifacts (gitignored, regenerated by build.sh)
```

## What was changed from the stock config

- `nero_gripper_moveit_config/config/nero.urdf.xacro` — self-contained kinematic
  tree copied from `../urdf/nero_arm.urdf`, renamed to `<robot name="nero">` to
  match `config/nero.srdf`. No `<xacro:include>` of `agx_arm_description`, no
  `nero.ros2_control.xacro` (the sim is the controller).
- `config/kinematics.yaml` — deduped (two `arm:` keys collapsed to one), KDL
  solver for the `arm` group.
- `config/moveit_controllers.yaml` — unchanged; `arm_controller` /
  `gripper_controller` `FollowJointTrajectory` actions already match the
  bridge's action servers (`sim/bridge/bridge_node.py`).
- Frames: planning frame = `base_link` (= `world`, fixed identity offset),
  arm chain `base_link → gripper_flange`. The bridge publishes `/joint_states`
  (joint1..7 + `gripper`) and `/tf` (`world → base_link` static + arm links).

## Build (one-time)

```bash
bash moveit/build.sh
source moveit/ws/install/setup.bash
```

## Run headless

```bash
# 1. MuJoCo bridge (repo-local .venv; publishes /joint_states + /tf, serves the actions)
bash sim/start.sh

# 2. move_group (MoveIt planner: /compute_fk, /compute_ik, /compute_cartesian_path)
source /opt/ros/humble/setup.zsh
source moveit/ws/install/setup.zsh
ros2 launch nero_gripper_moveit_config move_group.launch.py

# 3. Cartesian demo (ready bend -> FK flange -> Cartesian path -> execute)
export PATH=/usr/bin:$PATH && source /opt/ros/humble/setup.zsh
python3 moveit/cartesian_demo.py 0.05 0 0
```

`cartesian_demo.py [dx dy dz] [--no-ready]` does not use `moveit_py` /
`moveit_commander` (not installed on Humble here); it drives the raw services:

- `/compute_fk` (`GetPositionFK`) — current `gripper_flange` pose.
- `/compute_cartesian_path` (`GetCartesianPath`) — straight-line flange move →
  joint trajectory for `arm`.
- `/arm_controller/follow_joint_trajectory` — execute it.

## Verified result

From a non-singular pose, `cartesian_demo.py 0.05 0 0` prints:

```
plan ok: N points, fraction=1.000
arm_controller result: error_code=0
max joint displacement after execute: ~0.03 rad
```

## Known limitations

- **Straight home pose is near-singular.** At `joint1..7 = 0` the arm points
  straight, and KDL IK returns `NO_IK_SOLUTION` (`error_code -31`) for
  upward/outward flange steps. The demo bends the elbow (`joint2=0.4,
  joint4=0.2`) first via the same `FollowJointTrajectory` action.
- **Overdamped dynamics.** The vendored model uses `damping=2000`, so the bridge
  reports success once a trajectory point is *commanded*, not settled. The demo
  polls `/joint_states` until the ready pose settles before planning.
- **Gripper state.** The bridge publishes a single `gripper` width, not
  `gripper_joint1/2`, so `move_group` logs
  "complete state ... Missing gripper_joint1, gripper_joint2" and the `gripper`
  group's state is stale. Arm (joint1..7) planning is unaffected.
- **`ros2` CLI may hang** in this WSL2 environment (daemon discovery); the demo
  uses `rclpy` directly and does not need the CLI.
